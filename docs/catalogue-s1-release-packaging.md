## Prepare an Actions artifact

1. Keep the independently reviewed inner `v478-frontend-assets.zip` and capture evidence in owner-controlled storage. Verify the inner SHA-256 and exact manifest SHA-256 against the committed provenance. Preserve the ZIP bytes.
2. After separate approval and when the reviewed upload workflow is on protected main, the owner stages that ZIP as a GitHub Release asset in this repository. The Release asset ID is the input to **Prepare reviewed v478 assets artifact**. Use an owner-controlled Release and avoid an unrelated publication or deployment. A draft staging Release can be used if its binary is accessible to the owner workflow's read credential. Stop if GitHub does not return the exact asset ID, uploader, expected digest or size.
3. The owner dispatches the preparation workflow once on main with the exact Release asset ID. Stage validates the retained assets before the pinned upload action wraps the verified capsule as the single `v478-frontend-assets.zip` member. The workflow has read-only repository permissions and no deployment environment. The upload action uses its job-scoped artifact service.
4. Read back the completed source run, artifact ID, GitHub ZIP digest and expiry from the provider. Check that the outer API ZIP digest agrees with the upload output. Review the three digests for the outer GitHub ZIP, unchanged inner capsule and inner manifest.
5. The workflow requests 30 days of artifact retention, subject to the repository limit. Keep the sealed inner capsule and its receipts independently for rollback and future release preparation. If the Actions artifact expires, stage the same retained capsule through a fresh owner-approved run on main. Record the new artifact ID, source run, expiry and outer digest and obtain a fresh review. Never substitute a same-name artifact or recompute the pinned inner digest from a rebuild.

## Release and recovery

For each release dispatch, supply `v478_assets_run_id`, `v478_assets_artifact_id`, `v478_assets_github_zip_sha256` and `v478_assets_manifest_sha256`. The Release Assistant forwards the same values from `PUBLIC_RELEASE_V478_ASSETS_RUN_ID`, `PUBLIC_RELEASE_V478_ASSETS_ARTIFACT_ID`, `PUBLIC_RELEASE_V478_ASSETS_GITHUB_ZIP_SHA256` and `PUBLIC_RELEASE_V478_ASSETS_MANIFEST_SHA256`.

Both jobs check the specific artifact and its successful owner-dispatched source run, fetch the raw Artifact API ZIP and compare its pinned digest before parsing. The GitHub credential is sent only to the GitHub API. The temporary signed download URL is not logged. The Python validator checks both nested ZIP inventories before writing files, rejects links, traversal and repeated paths, and caps the outer ZIP at 8 MiB, the inner capsule at 7 MiB, expanded bytes at 12 MiB and each inner member at 4 MiB. It reuses the existing JS packager for the verified hashed assets, and copies the verified Workbox module only if its path is absent or byte-identical in the new build. A conflict blocks the workflow. The existing live preflight, final owner approval, Public-only deploy, postflight and historical evidence remain in force.

If packaging fails, the production release stops before deployment. Review the proof, correct the archival issue and start a newly authorized release.
