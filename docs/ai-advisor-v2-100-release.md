## Target and what “100%” means

```text
AI_ADVISOR_V2_MODE=canary
AI_ADVISOR_V2_CANARY_PERCENT=100
AI_ADVISOR_RETRIEVAL_COMPLETENESS_ENABLED=false
AI_ADVISOR_DOCUMENT_CLOUDFLARE_FIRST_ENABLED=false
AI_ADVISOR_DOCUMENT_CLOUDFLARE_FIRST_PERCENT=0
```

Keep `canary` mode deliberately: all eligible authenticated users are selected,
but the existing grounded legacy fallback and canary telemetry remain intact.
Changing mode to `on` would change failure/fallback semantics and is NOT this PR.
Selection does not promise every question is generated by V2 or that V1 disappears.

`ai-advisor.ts` resolves authenticated identity, consent, quota, structured
context and zero-AI answers before evaluating V2. Personal grades/conduct,
schedules, course catalogue and general questions retain their current routing.
Only document intents enter the selected V2 path. The runtime searches authorized
public completed candidates (bounded metadata pagination), uses vector topK 3
and threshold .4, then validates evidence/source IDs and rechecks D1 authorization.
The flag does not create access to private documents or personal scores.

In `canary` mode, unavailable retrieval, no usable documents, empty/dropped
results, generator fault/timeout, abstention or invalid grounding fall through
to the existing legacy document path. Gemini needs authorized, relevant evidence
and valid citations; otherwise the response abstains safely. Quota survival
does not permit an ungrounded general model to answer an official question.
Successful V2 answers do not incur a Gemini fallback call.

## Fixed transition and effective vars

`check-public-release-state.mjs --predeploy` requires **exactly canary/7** before
release and a config target of **exactly canary/100**. Only that single reviewed
percentage delta is allowed. Other config variables, bindings, observability
and 0054 columns still pass the existing drift gates. Missing document OFF flags
are tolerated ONLY on the old version, never on the new serving version.

The reader is fixed to the Public account, Worker and D1 UUID. Its only SQL is
`PRAGMA table_info(ai_documents)`; no migration or business-record query exists.
It requires a single version at 100% traffic, reads that version's bindings,
and records only the non-sensitive previous version ID as a job output.

The workflow retains the complete owner/exact-SHA/PAT/protection guard immediately
before `wrangler deploy --config cloudflare/wrangler.jsonc --keep-vars`.
The locked Wrangler 4.115.0 upload sends the explicitly configured percentage
`100` alongside `keep_bindings` for `plain_text` and `json`. The explicitly
configured target is present in the actual multipart upload, not omitted in
favor of retaining the old percentage. Unspecified dashboard vars are retained.
The offline CLI protocol test checks the actual upload, not a hand-written CLI simulation.
[Wrangler flag documentation](https://developers.cloudflare.com/workers/wrangler/commands/workers/#deploy)

`--postdeploy` is mandatory after a successful deploy. It reads settings,
deployments and the actual serving version. It requires a NEW version (not the
preflight ID), single-version 100% traffic, **canary/100** and explicit OFF/OFF/0
in the serving bindings. Retention of 7, split traffic, missing metadata, provider
HTTP error or any drift fails closed. It does not retry a write or auto-rollback.
An offline protocol test is not evidence that the GitHub environment token can
deploy production or that live vars have changed; that proof remains the future
approved release's read-only postflight.

## Remaining risks / release blockers

1. **Credential capability:** secret names and account-token scope were verified
   previously; the environment credential has not been exercised against the
   entire deployment path (routes, queue consumers, Workflows). Do not expand
   privileges or relax guards automatically. Resolve this with owner approval.
2. **Documents and quality:** raising selection does not upload/reindex the new
   Word corpus. The 60 staging Word-first passes used the separate Cloudflare-first
   completeness path. With completeness OFF, this release does NOT promise those
   results: incomplete tables, lower recall or more safe abstentions/fallbacks
   remain possible. Owner must explicitly accept this distinction or postpone
   rollout until the separately authorized production document-readiness process.
3. **Usage:** up to 100/7 (~14.3x) as many eligible document requests can attempt
   V2, not 14.3x all app traffic or a measured USD bill. Failing V2 may then pay
   for Gemini as well. Existing quota, caches and per-request bounds are unchanged.
   Monitor `search_calls`, `workers_ai_calls`, `gemini_calls`, cache hit rate,
   fallback, abstention, invalid citations, timeouts and p50/p95 latency. Provider
   token/cost counters may be unavailable; do not present estimates as measured cost.
4. No production provider tests or 100% live smoke have run for this PR.
5. Time Travel recovery is not a Worker rollback and is not authorized here.

## Owner-controlled release sequence and stop points

1. Review this PR and local/PR CI; owner merges only after explicit approval.
   Main changing means the old SHA/approval cannot authorize this release.
2. Run independent **validation-only** workflow on the NEW exact main SHA.
   Verify its check/run provenance and success. Keep the deployment workflow
   disabled until owner separately approves enabling only this manual workflow.
3. Record current Public version/config and confirm the fixed 7% baseline,
   production 0054 schema, token capability and desired quality/usage risk.
   Any drift: STOP, no broad migration/deploy fallback.
4. Owner dispatches a NEW release run on main with the new approved SHA, then
   separately records `PUBLIC_RELEASE_APPROVAL_SHA` and
   `PUBLIC_RELEASE_APPROVAL_RUN_ID` in `public-production` after dispatch.
   Keep main-only, wait >=5 minutes, no admin bypass, strict branch protection.
   No approval variables, settings or secrets are changed by this PR.
5. Validation -> exact predeploy state -> final approval -> Public-only deploy ->
   read-only serving-version postflight. Auth, D1 data, R2 data, indexes and
   documents are not deployment targets. If any step fails, STOP and diagnose.
   A failed postflight can mean the Worker changed: never report release success.
6. Use existing no-PII telemetry first. Any live question/provider benchmark,
   Word upload/indexing or flag enablement needs its own authorization.
7. Owner-approved rollback: restore the recorded previous Public Worker version
   AND verify actual 7% serving configuration, bindings/observability and document
   OFF flags. If version rollback does not restore settings, STOP and seek exact
   configuration-change approval; do not blindly rerun this 7->100 workflow.
   No Auth rollback, D1 restore, source deletion or automatic repair is permitted.
